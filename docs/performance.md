# ローカルで Gateway と処理キューを測る

Akari の実行環境で、処理枠を使い切ったときの Gateway の応答と、独立したイベントハンドラーの遅延を測れます。Bot トークンは不要です。

```sh
cargo test --release --locked --lib gateway_runtime::tests::performance:: -- --ignored --nocapture --test-threads=1
```

`--release` は最適化済みコードを使います。`--test-threads=1` で2本の計測を順番に実行します。比較するときは同じマシン、Rust バージョン、負荷条件で複数回測ります。出力の時間はマイクロ秒で、`n`、p50、p95、p99、最大値が記録されます。

## キューとワーカー

空いている状態で、500件の投入からハンドラー開始までを測ります。次に4つのワーカーを待機させ、64件のキューに256件を連続投入します。キューに入らず拒否された件数と、キューから出た後に全ワーカーが埋まっていて拒否された件数を別々に数えます。

## Gateway とコマンドが競合した場合

ループバック WebSocket から通常時とワーカーを使い切った場合に、それぞれ50件ずつ計測します。

- Gateway がイベントを送ってから、独立した `on_message` が受け取るまで。
- Gateway がハートビートを要求してから、Bot の応答が戻るまで。
- 全ワーカーが埋まった状態で256件のコマンドを送ったときの、混雑扱いの件数と拒否時刻。直後に要求したハートビートの応答も計測します。

件数と応答の受信をテストで検証します。遅延値は比較に使えるよう出力します。計測範囲は同一マシン上の Gateway・処理キューです。Discord の RTT、REST のレート制限、複数ホスト間の速度を調べる場合は、その環境を使って別途測定します。

## 記録例

Windows（ビルド 26300、24 論理プロセッサー）、Rust 1.90.0 の最適化ビルドを5回続けて実行した結果です。表の範囲は各回の値の最小から最大です。

| 測定区間 | 通常時の p95 | 4 ワーカーが待機中の p95 |
| --- | ---: | ---: |
| Gateway 送信から `on_message` | 54.6〜81.8 µs | 42.8〜71.6 µs |
| ハートビート要求から応答 | 85.4〜103.1 µs | 50.7〜88.7 µs |

256件のコマンドを連続投入した直後のハートビート応答は101.5〜153.1 µsでした。各回とも256件を混雑として扱いました。別に行ったキュー単体の試験では、各回とも192件がキュー満杯、64件が実行枠不足で拒否されました。

## キャッシュの上限とプロセスメモリを測る

以下は1件ずつ別のプロセスで実行します。既定値ではそれぞれ81,920件を投入し、最新16,384件だけが保持されることを全IDで検証します。キャッシュ挿入、メッセージ編集、メンバー取得の1操作あたりの所要時間も記録します。

```sh
cargo test --release --locked --lib cache_measurement::message_cache_fill_and_churn -- --ignored --exact --nocapture
cargo test --release --locked --lib cache_measurement::member_cache_fill_and_churn -- --ignored --exact --nocapture
```

- `AKARI_CACHE_MEASURE_CAPACITY` は保持数です。1〜250,000の範囲で変更できます。
- `AKARI_CACHE_MEASURE_PAUSE_MS` を設定すると、空、満杯、4回の置き換え後の計6段階で停止します。0〜60,000 msを指定できます。各行の `pid` を使って停止中に採取します。比較するときは各プロセスの同じ段階を採取してください。
- Windows では別の PowerShell から `Get-Process -Id <PID> | Select-Object WorkingSet64, PrivateMemorySize64` を実行します。Linux では `/proc/<PID>/status` の `VmRSS` を読みます。

`retained_model_inline_bytes` と `retained_string_bytes` はモデルの本体と選んだ文字列の合計です。インデックス、ほかの動的領域、アロケーターやテストバイナリ全体の分は OS 側の値に含まれます。メッセージの編集は前後のスナップショットを扱うので、単純なメンバー取得とは処理範囲が異なります。

### Windows での測定例

Rust 1.90.0 の最適化ビルドで各条件を別プロセスとして実行しました。ワーキングセットは実行ファイルやアロケーターを含む、プロセス全体の値です。メッセージ本文は256バイト、メンバーのロールは3件の固定入力です。

| キャッシュ | 保持数 | 空のワーキングセット | 満杯 | 4回置換後 | 4回置換後のプライベートメモリ |
| --- | ---: | ---: | ---: | ---: | ---: |
| メッセージ | 4,096 | 6.6 MiB | 22.4 MiB | 22.7 MiB | 19.6 MiB |
| メッセージ | 16,384 | 6.6 MiB | 69.3 MiB | 69.8 MiB | 67.6 MiB |
| メンバー | 4,096 | 6.5 MiB | 9.5 MiB | 9.6 MiB | 6.3 MiB |
| メンバー | 16,384 | 6.5 MiB | 17.9 MiB | 18.0 MiB | 14.9 MiB |

16,384件の条件では、それぞれ81,920件のうち65,536件が追い出され、残ったIDは最新の16,384件と一致しました。ワーキングセットは1回目の置き換えから4回目まで、採取した各段階で同じ値でした。メッセージ編集のヒットは平均2.65 µs、メンバー取得のヒットは平均0.17 µsでした。本文の長さ、埋め込みや添付の有無が異なる Bot では、メモリの数字も変わります。
