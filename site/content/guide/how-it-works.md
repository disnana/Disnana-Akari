# Akari の動き方

Akari が、届いたイベントをどう扱うかを知っておくと、「遅いコマンドがあるとどうなる？」「混雑したら？」が分かります。

## 全体の流れ

```text
Discord ──▶ [受信ループ] ──▶ キュー ──▶ ハンドラー（並行して実行）
              │                │
              │                └─ いっぱいのとき: on_error に報告（スラッシュ・ボタンは本人にだけ返信）
              └─ 受信だけを担当。重い処理はしない
```

受信ループは、Discord からのイベントを受け取って、種類ごとのキューに入れるだけです。ハンドラーの処理を待たないので、ハンドラーが遅くても、接続を保つための通信（ハートビート）は止まりません。

## 種類ごとの実行枠

| 処理 | 同時に動かせる数 | 待てる数 | いっぱいのとき |
| --- | --- | --- | --- |
| テキストコマンド | 8 | 64 | `on_error` に報告します。返信は、`Messages::text_command_busy` を設定した場合だけです。 |
| スラッシュコマンド、ボタン、選択メニュー、フォーム | 合計 8 | 合計 64 | `on_error` に報告し、本人にだけ「現在混雑しています」と返します（`Messages::interaction_busy`）。 |
| `on_ready`、`on_message`、`Bot::run` の自前ハンドラー | 1（受信順） | 64 | 新しいイベントを捨てて、`on_error` に報告します。 |

つまり、**コマンドとボタンは並行** して動き、**`on_ready` と `on_message` は 1 件ずつ受信順** に動きます。

> [!NOTE]
> 「同時」は、複数のスレッドではなく、1 つのタスクの中で `.await` の待ち時間を使って交互に進める、という意味です。`current_thread` のランタイムでも並行して動きます。

## 長い処理に気を付ける

ハンドラーが `.await` で待っている間は、ほかの処理が進みます。逆に、**待たずに** CPU を使い続ける処理（重い計算、同期的なファイル読み込み、`std::thread::sleep` など）は、ほかの処理も止めてしまいます。

```rust
use disnana_akari::{CommandContext, Result};

async fn heavy(ctx: CommandContext<'_>) -> Result<()> {
    // 重い計算は、専用のスレッドに逃がす
    let answer = tokio::task::spawn_blocking(|| (1..=1_000_000u64).sum::<u64>()).await?;
    ctx.reply(&format!("答えは {answer} です。")).await
}
```

> [!TIP]
> `spawn_blocking` は Tokio の `rt` 機能で使えます。非同期のライブラリ（HTTP クライアントなど）を使うときは、そのまま `.await` で待てば十分です。

## 3 秒ルールとキュー待ち

スラッシュコマンドやボタンは、Discord が **受信から 3 秒** 以内の最初の応答を求めます。キューで待っている時間も含まれるので、混雑時や遅いハンドラーがあるときは、`defer` を最初に呼ぶのが安全です。[応答のしかた](responding.md)

キュー待ちの時間は、`ctx.timing().queue_wait()` で測れます。

## 終了のしかた

Discord との接続が切れても、復旧できる切断は自動で再接続されます。復旧できない状態になったときだけ、`run_commands` や `start` が `Err` を返して終了します。そのとき、処理中や待機中のイベントは中止されます。
